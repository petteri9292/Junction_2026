0:00–0:25 — SLIDE 1: THE READER AND THE PROJECT

SAY:
“Hi, I’m Petteri. WikiLens is my entry to MariaDB’s RAG track.

It lets readers ask questions about Finnish Wikipedia and get an article with
source passages they can inspect. I built the complete path from a question,
through retrieval over 568,416 articles, to generation, review and citations.”

ACTION: Advance to slide 2. Do not begin with the context comparison.

0:25–1:35 — SLIDE 2: THE PIPELINE

SAY:
“First, Qwen creates a hypothetical search passage and detects the question’s
language in one structured response. The passage guides search; it is never
source evidence.

BGE-M3 embeds that passage. MariaDB stores the article text, revision metadata
and native vectors together. Its indexed vector search retrieves candidate
articles through SQL.

Next, I split the articles at their headings and use a cross-encoder to rerank
the passages. That selects the evidence for the writing step.

Qwen writes an article in the detected language from those passages. Another
pass reviews the draft against the sources. Then the citation stage selects
source spans, and Python copies and checks the exact quotations.

The database, passage selection and writing steps all connect to the same
inspectable source records.”

ACTION: Point down the process as you speak. Give MariaDB's role a pause.
Do not rush through model version strings or recite every label.

SAY:

Is this the RAG track or the time-travel track?
“The RAG track. I preserve and link source revision metadata. I have not built
system-versioned-table or point-in-time Wikipedia queries.”

What is original about it?
“I combined language detection into the existing structured HyDE call, carried
context through evidence selection, and connected reviewed prose to exact
source spans in a reading interface. I’m demonstrating the integrated reader
workflow, not claiming to have invented RAG or trained a new foundation model.”

Why MariaDB?
“It stores the article text, revision metadata and native vectors together.
SQL retrieves the vector candidates and the corresponding source records.”

What did you build yourself?
“I integrated the full-corpus retrieval pipeline, context handling, passage
selection, language routing, generation, review, citation extraction and the
reading interface. The underlying models are pretrained.”

How does language detection work?
“The existing HyDE call returns a Pydantic-constrained object: hypothetical
passage first, then a nullable language code. Only the passage is embedded.
The code controls generation and review. Unknown language falls back to Finnish.
The retrieval passage stays Finnish because this corpus is Finnish.”

Is there a final LLM fact-check after the citations are attached?
“No. The draft review happens before citation attachment. Later model calls
select quotation spans, and Python validates literal matches. That is not an
independent check of factual support.”

How fast is it?
“In two live language-routing checks, the English question took 16.8 seconds and
the Finnish question 20.6 seconds, including retrieval but excluding startup.
Those are two measurements, not a general latency guarantee.”
Source: reports/metrics.json. These are different questions
from the earlier talvisota/context demonstration, so do not present the numbers
as a measured head-to-head comparison of those two context settings.

Why does this matter to a reader?
“It combines a focused explanation with access to the source passages, so the
reader can check the evidence without manually assembling every part of the
answer across several Wikipedia pages.”

What still needs work?
“Finnish prose quality and claim-to-source support. The review pass does not
reliably fix every error. I would evaluate those explicitly before calling the
answers dependable.”

IF YOU ONLY HAVE 30 SECONDS

“WikiLens is a MariaDB RAG application over 568,416 Finnish Wikipedia articles.
It retrieves and reranks evidence, writes and reviews an article in the reader’s
language, then attaches inspectable source quotations. The main achievement is
that complete pipeline working on the full dataset.”

HOW THE PITCH ADDRESSES THE SUPPLIED CHALLENGE

MariaDB use (20%): Explain the native indexed vector retrieval and how SQL
connects vectors with the stored article text and revision metadata.
Implementation (20%): Show the full Dataset L count and describe passage-level
selection, the generation/review stages and the resident serving setup.
Usefulness (20%): Show an English question yielding an article from Finnish
sources, with direct access to the original evidence.
Design/demo (20%): Let reviewers see one question, the returned article and
one source card. Use large text and simple window switching.
Originality (20%): Explain the combined workflow and specific integration work,
without claiming that RAG, embeddings or vector search are new inventions.

The challenge also describes SVT/time travel. This project chose the RAG track.
Do not imply that stored source revision links implement temporal queries.
Do not read the criteria list to reviewers; use it to prepare the story.
